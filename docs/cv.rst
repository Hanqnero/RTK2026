Распознавание дорожных знаков
=============================

Штатный детектор работает на Raspberry Pi 5 рядом с USB-камерой. Он запускает
ONNX-модель YOLO через ONNX Runtime и публикует не изображение, а компактное
сообщение ``DrivingDetection`` для ``city_nav``. Отдельный контейнер сохраняет
независимый жизненный цикл камеры: аппаратный стек продолжает работать, если
камера отключена или модель не загрузилась.

Запуск
------

.. code-block:: bash

   docker compose -f pi/docker/docker-compose.pi.yml stop camera
   docker compose -f pi/docker/docker-compose.pi.yml up -d --build perception
   docker logs -f rtk2026-perception

Сервис запускает ``rtk2026_cv/sign_detection.launch.py`` с профилем
``sign_detection_pi5.yaml``. Launch находит ``best.onnx`` через ament index,
поэтому путь не зависит от раскладки workspace. ``camera`` и ``perception``
в одном compose-файле — альтернативные режимы и не могут одновременно
открывать ``/dev/video0``.

Производительность
------------------

Начальная конфигурация использует вход 416 пикселей и два inference thread.
Подписка на камеру имеет очередь глубиной один: при перегрузке пропускаются
старые кадры, а не накапливается задержка. Периодический лог содержит
``inference`` и ``source_age``; второй показатель не должен постоянно расти.

Поднимать вход до 640 следует только после прогона вместе с локализацией и
Nav2 с контролем ``docker stats``, температуры и throttling Pi.

Включение в маршрутизацию
-------------------------

``city_nav`` при ``min_box_area_px: 0.0`` намеренно не подписывается на
детекции: без калибровки далёкий знак можно приписать неверному перекрёстку.
Для включения подъедьте к точке принятия решения, запишите
``route_box_area`` из ``/perception/driving_detection`` и внесите измеренный
порог в ``rtk2026_city_nav/config/city_nav.yaml``. Диагностика затем проверяет
и наличие publisher, и свежесть сообщений.

Классы модели
-------------

Модель содержит ``bus_stop``, пять маршрутных знаков, ``obstacle`` и
``parking_spot``. Унаследованная интеграция преобразует класс 4
``obstacle`` в ``bus_detected``. Эта неоднозначная привязка оставлена явно,
чтобы не менять поведение модели молча; перед финальным прогоном её нужно
сверить с разметкой датасета и правилами трассы.

.. warning::

   Текущий ``best.onnx`` не является пройденной приёмкой точности. Сохранённые
   тестовые картинки подтверждают известную из обучения путаницу направлений:
   правый знак может выходить как ``turn_left``. Развёртывание и транспорт
   детекций готовы, но перед включением ненулевого ``min_box_area_px`` нужны
   дообученные веса и повторная проверка всех классов.
