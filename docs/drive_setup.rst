Полный цикл настройки привода
=============================

Регламент одного прохода: от платы, на которую ещё ничего не залито, до
привода, который держит заданную скорость. ROS 2 здесь не участвует ни на
одном шаге — всё общение идёт по протоколу v2 напрямую с платой, поэтому
цикл выполняется до того, как поднят любой ROS-узел.

Страница даёт последовательность и команды. Почему шаги стоят именно в таком
порядке — в :doc:`pc/tools`, устройство прошивки — в :doc:`arduino/firmware`,
формат провода — в :doc:`arduino/protocol`.

.. important::

   На шагах 1–7 робот стоит на подставке, колёса не касаются пола. На пол он
   опускается только на шаге 8. Колесо, вращающееся под нагрузкой пола, даёт
   другую установившуюся скорость, и снятый на полу feedforward неверен.

Где какая величина живёт
------------------------

Это определяет цену ошибки на каждом шаге: часть настройки уходит в EEPROM
и меняется на лету, часть прибита к прошивке и требует перезаливки.

.. list-table::
   :header-rows: 1
   :widths: 34 22 44

   * - Величина
     - Где хранится
     - Как меняется
   * - ``k*Reverse`` (ориентация железа)
     - константа прошивки
     - правка ``motor_interface.h`` и перепрошивка
   * - ``kEncoderPulsesPerMotorRev``, ``kGearRatio``
     - константа прошивки
     - правка ``motor_interface.h`` и перепрошивка
   * - ``kWheelRadiusM``, ``kTrackWidthM``
     - константа прошивки
     - правка ``motor_interface.h`` и перепрошивка
   * - ``k_static``, ``k_velocity`` (feedforward)
     - EEPROM
     - ``identify_wheel.py --apply --save``, без перепрошивки
   * - ``kp``, ``ki``, ``kd``
     - EEPROM
     - ``tune_wheel.py``, действуют сразу, ``save`` фиксирует

Коэффициенты в ``motor_interface.h`` нулевые намеренно: это запасные значения
на случай пустой или битой EEPROM, а рабочие снимаются стендом.

Выйти из заведомо неудачной настройки можно, не перепрошивая плату: маска
``RESET_GAINS_TO_DEFAULT`` возвращает скомпилированные коэффициенты и стирает
запись в EEPROM. Отдельного ключа в инструментах у неё нет, отправляется она
через ``BenchLink``:

.. code-block:: bash

   cd pc
   .venv/bin/python -c "
   import sys; sys.path[:0] = ['tools', '../protocol']
   from bench import BenchLink
   with BenchLink('$RTK_LINK', 115200) as link:
       link.reset(gains_to_default=True)
       print(link.get_gains())
   "

В ответ приходят два отчёта о коэффициентах: по полю источника видно, что
плата вернулась к скомпилированным значениям.

Шаг 0. Хост и транспорт
-----------------------

Плата подключена либо к тому же компьютеру, где запускаются инструменты, либо
к Raspberry Pi — тогда порт держит ретранслятор, а инструменты идут к нему по
TCP. Кодек, кадры и CRC при этом одни и те же, см. :doc:`bench`.

Окружение на ноутбуке:

.. code-block:: bash

   cd pc
   python3 -m venv .venv
   .venv/bin/pip install -r requirement.txt

Дальше в командах используется ``$RTK_LINK`` — адрес платы. Один из двух
вариантов:

.. code-block:: bash

   export RTK_LINK=/dev/ttyUSB0          # плата в этом же компьютере
   export RTK_LINK=192.168.1.50:5555     # плата на Raspberry Pi

Для второго варианта на Pi поднимается ретранслятор:

.. code-block:: bash

   # на Raspberry Pi
   ls -l /dev/serial/by-id/                                   # найти устройство
   docker compose -f pi/docker/docker-compose.pi.yml up link

Путь по идентификатору устройства подставляется в секцию ``devices`` файла
``pi/docker/docker-compose.pi.yml``: он не меняется при перезагрузке,
в отличие от ``/dev/ttyUSB0``.

.. important::

   Порт держит ровно один процесс. Ретранслятор, прошивка и ROS-нода
   ``arduino_bridge`` конкурируют за одно устройство. Перед прошивкой
   остановите ретранслятор.

Шаг 1. Прошить плату
--------------------

С Raspberry Pi, тулчейн и ``avrdude`` живут в контейнере:

.. code-block:: bash

   cd ~/RTK2026
   docker compose -f pi/docker/docker-compose.pi.yml run --rm build   # только сборка
   docker compose -f pi/docker/docker-compose.pi.yml run --rm flash   # сборка и заливка

С ноутбука, если плата воткнута в него:

.. code-block:: bash

   cd arduino
   cmake --preset macos-system -DUPLOAD_PORT=/dev/cu.usbmodem14101
   cmake --build build --target flash

Пресеты под другие платформы и обход отсутствия Homebrew — в
:doc:`arduino/build`. Отдельный ``shell`` в compose на Pi даёт ту же среду
интерактивно, когда нужно поработать с ``avrdude`` руками:

.. code-block:: bash

   docker compose -f pi/docker/docker-compose.pi.yml run --rm shell

Шаг 2. Убедиться, что связь есть
--------------------------------

.. code-block:: bash

   cd pc
   .venv/bin/python tools/log_telemetry.py --port $RTK_LINK --stats

Что должно быть видно: строки идут без разрывов в ``seq``, ``dt_us`` держится
около 25 000, в статистике ``rx_bad_crc`` и ``rx_resync`` не растут. Разрывы
``seq`` означают потерю пакетов, рост ошибок CRC — проблему канала, а не
прошивки.

Шаг 3. Энкодеры и знаки
-----------------------

.. code-block:: bash

   .venv/bin/python tools/check_encoders.py --port $RTK_LINK --auto
   .venv/bin/python tools/verify_signs.py   --port $RTK_LINK

Первая команда крутит каждое колесо прямым PWM и выносит вердикт по каждому
пункту: отвечает ли энкодер, совпадает ли знак дельты с направлением команды,
не крутится ли второе колесо, насколько колёса симметричны. Вторая проверяет
тот же контракт через кинематику корпуса, поэтому ловит заодно и неверную
``kTrackWidthM``.

Асимметрия колёс дефектом не является: моторы редко одинаковы, и дальше каждое
колесо настраивается отдельно. Дефекты — молчащий канал, неверный знак,
перекрёстное вращение.

При неверном знаке правится ровно один флаг ``k*Reverse`` в
``motor_interface.h`` и ничего больше: компенсирующих минусов в коде быть не
должно. После правки — снова шаг 1.

Ручной режим, когда надо покрутить колесо рукой или поймать дребезг на
конкретном участке:

.. code-block:: bash

   .venv/bin/python tools/check_encoders.py --port $RTK_LINK --drive --log records/enc.csv

Шаг 4. Отсчёты на оборот колеса
-------------------------------

.. code-block:: bash

   .venv/bin/python tools/calibrate_encoder.py --port $RTK_LINK --manual --turns 10

Колесо проворачивается рукой на целое число оборотов, мотор при этом
обесточен. Это самый точный режим: нет ни нагрузки, ни проскальзывания.
Режим ``--powered`` крутит колесо само, но опирается на паспортные обороты,
поэтому годится для проверки, а не для первичного измерения.

Измеренное число раскладывается на ``kEncoderPulsesPerMotorRev`` и
``kGearRatio`` в ``motor_interface.h``, после чего — снова шаг 1. Вывести эту
величину из паспорта нельзя: энкодер JGB37-520 стоит на валу мотора, до
редуктора, паспорт даёт обороты выходного вала, а не отношение.

Пока это число неверно, все скорости выражены в неверных единицах, и всё
настроенное дальше настроено под неверную шкалу.

Шаг 5. Feedforward
------------------

.. code-block:: bash

   .venv/bin/python tools/identify_wheel.py --port $RTK_LINK --wheel both --apply --save --plot

Ступеньки PWM в обход регуляторов: снять зависимость установившейся скорости
от PWM можно только при разорванной обратной связи. По точкам, где колесо уже
вращается, строится прямая ``pwm = k_static + k_velocity * скорость``.

Каждое колесо измеряется отдельно и в обе стороны: моторы редко симметричны,
а трение вперёд и назад отличается почти всегда. ``--apply`` отправляет
коэффициенты в прошивку, ``--save`` пишет их в EEPROM. Перепрошивка не нужна.

Шаг 6. ПИД по колесу
--------------------

.. code-block:: bash

   .venv/bin/python tools/tune_wheel.py --port $RTK_LINK --wheel left  --plot --log records/tune_left.csv
   .venv/bin/python tools/tune_wheel.py --port $RTK_LINK --wheel right --plot --log records/tune_right.csv

Коэффициенты меняются на лету и действуют немедленно; до команды ``save`` они
живут только в оперативной памяти. По каждой ступеньке считаются время
нарастания, время установления, заброс, остаточная ошибка, доля времени
в насыщении PWM и доля feedforward в команде. Последняя величина показательна:
у хорошо настроенного контура она высока — ПИД правит небольшой остаток,
а не тянет весь сигнал.

Одна ступенька без интерактива, когда нужно проверить конкретную тройку:

.. code-block:: bash

   .venv/bin/python tools/tune_wheel.py --port $RTK_LINK --kp 3 --ki 5 --step 2.0

Зафиксировать результат в EEPROM и записать его же в YAML:

.. code-block:: bash

   .venv/bin/python tools/tune_wheel.py --port $RTK_LINK --wheel left --save --export records/gains_left.yaml

Шаг 7. Общие проверки
---------------------

.. code-block:: bash

   .venv/bin/python tools/monitor.py          --port $RTK_LINK --drive --log records/drive.csv
   .venv/bin/python tools/profile_firmware.py --port $RTK_LINK --duration 30 --csv records/profile.csv

Панель показывает обе стороны сразу: скорости с уставками, PWM, ошибку
слежения и качество связи. Управление стрелками по умолчанию идёт прямым PWM
в обход регуляторов — так панель работает и на ненастроенном роботе;
``--drive-mode setpoint`` проверяет уже настроенный контур.

Профилировщик разделяет джиттер прошивки и джиттер канала: первый берётся из
``dt_us``, измеренного самим MCU, второй — из разброса разности между временем
прибытия пакета и временем MCU в этом же пакете. По сети первый не меняется,
а второй растёт; именно это и отвечает на вопрос, чей срыв виден на графике.

Шаг 8. Маршрут на полу
----------------------

.. code-block:: bash

   .venv/bin/python tools/route_test.py --port $RTK_LINK --pattern triangle  --plot --log records/route.csv
   .venv/bin/python tools/route_test.py --port $RTK_LINK --pattern rectangle --plot
   .venv/bin/python tools/route_test.py --port $RTK_LINK --pattern figure8   --sweep

Единственный шаг, где робот стоит на полу. Замкнутый маршрут ловит то, чего
не видно на графиках отдельного колеса: одометрия строится не только из
скорости колеса, но и из двух геометрических констант. Ошибка в
``kWheelRadiusM`` даёт масштабную ошибку всего пути, ошибка в ``kTrackWidthM``
— систематический недоворот или переворот. На графике скорости оба дефекта
выглядят идеально.

``rectangle`` чувствительнее к колее, ``figure8`` компенсирует повороты
в разные стороны, ``--sweep`` прогоняет маршрут на нескольких скоростях: если
поправка зависит от скорости, причина не в геометрии, а в проскальзывании.

Логи и повторяемость
--------------------

Все инструменты принимают ``--log`` и пишут телеметрию в CSV одного формата
с колонкой фазы прогона. Каталог ``records/`` игнорируется git-ом: логи стенда
— данные конкретного прогона, а не код. Лог нужен даже при открытом окне:
график показывает текущий прогон, а сравнивать приходится с тем, что было
вчера.

Инструменты можно запускать и в контейнере, если не хочется ставить
зависимости на хост, — но окна Qt оттуда без настройки не работают, поэтому
годятся режимы ``--text`` и ``--no-plot``:

.. code-block:: bash

   docker compose -f pc/docker/docker-compose.tools.yml run --rm tools \
       python3 tools/check_encoders.py --port $RTK_LINK --auto --no-plot --log records/enc.csv

Подробности про контейнер и про окна из него на macOS — в :doc:`pc/index`.

Отдельные стендовые прошивки
----------------------------

Два варианта прошивки не участвуют в протоколе и печатают текст в порт. Они
нужны, когда надо отделить проблему платы от проблемы прошивки основного
контура.

.. code-block:: bash

   cd arduino
   cmake --preset motor_test_macos          # main_direct_motor_test.cpp
   cmake --build build --target flash

``main_direct_motor_test.cpp`` последовательно проверяет левый и правый мотор
в обоих направлениях, затем оба вместе, и каждые 100 мс печатает CSV с PWM
и дельтами. ``main_bmi270_test.cpp`` (опция ``ROBOT_BMI270_TEST=ON``)
инициализирует IMU и печатает raw accel/gyro; читать его вывод удобно так:

.. code-block:: bash

   cd pc
   .venv/bin/python tools/read_bmi270_console.py --port /dev/ttyUSB0 --timestamp

.. note::

   ``read_bmi270_console.py`` — единственный инструмент набора, который
   открывает serial-порт напрямую и сетевой адрес не принимает: он читает
   текстовые строки, а не кадры протокола, и через ретранслятор не работает.
   Для него нужна плата, подключённая к тому же компьютеру.

После стендовой прошивки на плату возвращается основная: шаг 1 без опций.
