Проверка транспорта между Raspberry Pi и ноутбуком
====================================================

Между малинкой и ноутбуком нет надёжного multicast, поэтому топики идут через
DDS Router по одному TCP-соединению. Страница описывает, как проверить эту
связку и как отличить настоящий отказ от ложного срабатывания. Команды
повседневного запуска - в :doc:`pi/index`.

Зачем это отдельный шаг
------------------------

Прежде чем запускать на роботе SLAM, Nav2 и остальную систему, надо доказать,
что данные вообще ходят между машинами. Иначе при первом же отказе будет
неясно, что сломалось: транспорт, QoS, прикладной код или конфигурация ROS.

Проверка живёт в ``docker/dds_check/`` и не содержит ни одного пакета проекта.
Один и тот же образ используется на обеих сторонах: роль задаётся переменной
``ROLE`` и командой, а не отдельной сборкой, поэтому расхождение версий между
машинами исключено как возможная причина отказа.

Как устроена проверка
----------------------

Обычный ``ros2 topic pub`` создаёт топик с volatile durability и reliable
reliability. Он не проверяет два случая, на которых как раз и держится работа
RViz через сеть, поэтому передатчик (``talker.py``) публикует три топика,
а приёмник (``listener.py``) считает по каждому не «что-то пришло», а
конкретные величины: сколько пакетов дошло, сколько номеров пропущено,
разброс интервалов, через сколько после старта пришло удержанное значение
и были ли перерывы длиннее порога.

.. list-table::
   :header-rows: 1
   :widths: 22 26 52

   * - Топик
     - QoS
     - Что ловит
   * - ``/check/volatile``
     - RELIABLE, VOLATILE
     - Базовый случай: идут ли данные вообще.
   * - ``/check/latched``
     - RELIABLE, TRANSIENT_LOCAL
     - Так публикуются ``/tf_static`` и карта. Подписчик, подключившийся
       позже, обязан получить последнее значение.
   * - ``/check/sensor``
     - BEST_EFFORT, VOLATILE
     - Так публикуются лидар и камеры. Проверяет согласование QoS
       на best-effort.

Есть также ``fake_robot.py`` — минимальный набор ``/tf``, ``/tf_static``,
``/map``, ``/scan``, ``/odom``, на котором оживает RViz целиком, а не только
числа в консоли.

Подготовка
----------

``PI_ADDRESS`` задаётся на **обеих** машинах одним и тем же значением —
адресом Raspberry Pi в локальной сети. На Pi он попадает в
``listening-addresses`` как адрес, который Router объявляет удалённой
стороне; на ноутбуке — в ``connection-addresses`` как адрес, который
ноутбук набирает. Если значения разойдутся, TCP-соединение установится,
топики будут видны на обеих сторонах, а данные не пойдут — см.
:ref:`transport-check-address-mismatch`.

.. code-block:: bash

   # Raspberry Pi
   cd ~/RTK2026/docker/dds_check
   export PI_ADDRESS=192.168.1.50        # собственный адрес Pi
   docker compose -f docker-compose.pi.yml build

   # ноутбук
   cd RTK2026/docker/dds_check
   export PI_ADDRESS=192.168.1.50        # тот же адрес Raspberry Pi
   docker compose -f docker-compose.mac.yml build

.. note::

   DDS Router входит не во все варианты образа Vulcanexus. Сборка падает
   сразу с понятным сообщением, если его нет. В этом случае соберите
   с другим вариантом::

      VULCANEXUS_TAG=jazzy-cloud docker compose -f docker-compose.pi.yml build

Путь 1: репетиция на одном ноутбуке
------------------------------------

Начинать стоит отсюда, даже когда Pi уже доступна. Значительная часть
отказов вызвана опечатками в конфигах, а не сетью, и на одной машине их
искать дешевле, чем гонять человека к роботу.

``docker-compose.local.yml`` поднимает обе стороны на одном ноутбуке —
в двух изолированных bridge-сетях без общего маршрута и без multicast между
ними. Это не срезание угла: единственный путь между ними — исходящее
TCP-соединение на опубликованный порт хоста, ровно как у настоящей
Raspberry Pi. Если поставить оба контейнера в одну сеть, они найдут друг
друга обычным DDS напрямую, и Router окажется вообще ни при чём — проверка
пройдёт, ничего не проверив.

.. code-block:: bash

   cd RTK2026/docker/dds_check
   docker compose -f docker-compose.local.yml build
   docker compose -f docker-compose.local.yml up -d robot_router robot viz

Что репетиция проверяет: конфигурацию Router, установление TCP-соединения,
прохождение топиков с разными QoS, late-joiner для TRANSIENT_LOCAL,
переподключение после обрыва и работу RViz через маршрут.

Что она не проверяет: настоящую сеть между двумя машинами — задержку, потери
на Wi-Fi, поведение при обрыве физической связи. Это покажет только
Raspberry Pi.

Посмотреть на данные и на RViz:

.. code-block:: bash

   docker exec rtk2026_viz bash -lc \
       'source /opt/vulcanexus/*/setup.bash; ros2 topic hz /odom'

   docker exec rtk2026_viz bash -lc \
       'source /opt/vulcanexus/*/setup.bash; ros2 topic echo /map --once'

   # RViz в браузере: http://127.0.0.1:6080/vnc.html

Числовой отчёт с той же стороны, где RViz:

.. code-block:: bash

   docker compose -f docker-compose.local.yml --profile tools up -d robot_talker

   docker exec rtk2026_viz bash -lc \
       'source /opt/vulcanexus/*/setup.bash; python3 /check/listener.py'

Поле проверки для обрыва связи и late-joiner — см. соответствующие шаги
:ref:`transport-check-hardware` ниже: процедура для них одинакова что
на реальных машинах, что здесь, только обрыв сети имитируется командой
Docker, а не выдёргиванием кабеля:

.. code-block:: bash

   docker network disconnect dds_check_viz_net rtk2026_viz
   sleep 15
   docker network connect dds_check_viz_net rtk2026_viz

.. note::

   Через маршрут не проходит ROS graph. Публикатор, созданный Router,
   виден как узел ``_CREATED_BY_BARE_DDS_APP_``, а ``Topic type hash``
   у него ``INVALID``. Диагностика, опирающаяся на граф, должна работать
   на стороне робота, а не здесь — см. :ref:`transport-check-next`.

Путь 2: настоящие Pi и ноутбук
--------------------------------

Пять шагов от «работает ли сеть вообще» до «переживает ли схема обрыв
связи». Каждый следующий шаг имеет смысл только если предыдущий прошёл.

1. Нужен ли Router вообще
~~~~~~~~~~~~~~~~~~~~~~~~~~

Сначала проверяется, проходит ли multicast. Если да, DDS Router может
не понадобиться, и незачем усложнять систему. Проверять надо **оба
направления** — односторонний тест ничего не доказывает.

.. code-block:: bash

   # Raspberry Pi
   docker compose -f docker-compose.pi.yml run --rm shell
   ros2 multicast receive

   # ноутбук, в host-режиме
   docker compose -f docker-compose.mac.yml run --rm shell-host
   ros2 multicast send

Затем наоборот: ``receive`` на ноутбуке, ``send`` на Raspberry Pi.

2. Работает ли обычный DDS
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Прошедший multicast ещё не означает работающий DDS: между ними остаются
обмен locator-ами, обнаружение endpoints и согласование QoS.

.. code-block:: bash

   # Raspberry Pi
   docker compose -f docker-compose.pi.yml run --rm talker

   # ноутбук, host-режим, БЕЗ Router
   docker compose -f docker-compose.mac.yml run --rm listener-host

Затем поменять направление: ``talker-host`` на ноутбуке, ``listener``
на Raspberry Pi.

.. list-table:: Толкование шагов 1-2
   :header-rows: 1
   :widths: 45 55

   * - Результат
     - Вывод
   * - multicast и pub/sub работают в обе стороны
     - DDS Router не нужен. Пропустите шаг 3.
   * - multicast работает, pub/sub нет
     - Проблема в locator-ах и виртуализации сети. Нужен Router.
   * - multicast не работает
     - Автообнаружение ненадёжно. Нужен Router.

3. Через DDS Router
~~~~~~~~~~~~~~~~~~~~

Router поднимается на обеих сторонах и держится запущенным всё время
проверки. Адрес Raspberry Pi подставляется на запуске из ``PI_ADDRESS``,
поэтому образ при смене сети пересобирать не нужно.

.. code-block:: bash

   # Raspberry Pi, отдельное окно
   docker compose -f docker-compose.pi.yml up router

   # ноутбук, отдельное окно
   docker compose -f docker-compose.mac.yml up router

Затем данные:

.. code-block:: bash

   # Raspberry Pi
   docker compose -f docker-compose.pi.yml run --rm talker

   # ноутбук
   docker compose -f docker-compose.mac.yml run --rm listener

4. Late-joiner
~~~~~~~~~~~~~~~

Главная проверка для RViz: он подключается к уже работающей системе и
должен получить статические трансформы и карту, опубликованные задолго
до его старта.

.. code-block:: bash

   # 1. Запустить talker на Raspberry Pi
   # 2. Подождать 2-3 минуты
   # 3. Только теперь запустить listener на ноутбуке

Критерий: в отчёте ``/check/latched: received = yes``. Если ``no`` —
TRANSIENT_LOCAL не прошёл через маршрут; см.
:ref:`transport-check-router-qos`.

5. Обрыв связи
~~~~~~~~~~~~~~~

.. code-block:: bash

   # 1. Всё работает, listener считает пакеты
   # 2. Отключить Wi-Fi или Ethernet ноутбука на 15-20 секунд
   # 3. Включить обратно
   # 4. Ctrl+C на listener

Критерий — не сам факт перерыва в отчёте (он неизбежен), а возобновился ли
поток после восстановления сети и не пришлось ли перезапускать Router.
Разбор чисел — в :ref:`transport-check-report`.

.. important::

   Восстановление потока не означает, что переживёт незавершённый вызов
   сервиса или action. TCP гарантирует доставку байт в рамках живого
   соединения, а не выполнение операции ровно один раз. Логику на этот
   счёт строить нельзя.

Как читать отчёт
-------------------

Ниже — отчёт локальной репетиции (Путь 1): обе стороны на одном ноутбуке,
две изолированные сети, приёмник подключён через 15 секунд после
передатчика, затем сеть на 15 секунд отключалась.

.. code-block:: text

   elapsed_s = 62.0

   /check/volatile:
     received = 309
     lost = 310 (50.08 %)
     first_message_after_s = 0.102
     rate_hz = 5.01
     interval_mean_ms = 199.78
     interval_max_ms = 34765.29
     jitter_stdev_ms = 1973.05
     gaps = 1
       gap at 11.7 s, duration 34.77 s

   /check/sensor:
     received = 272
     lost = 347 (56.06 %)
     rate_hz = 4.38
     gaps = 1
       gap at 11.7 s, duration 34.74 s

   /check/latched:
     received = yes
     after_s = 0.369

``lost``
    Ненулевое значение на volatile-топике при reliable QoS означает
    проблему вне обрывов связи: reliable-поток терять пакеты не должен.
    Здесь 50 % — это счёт до и после 15-секундного обрыва сети, а не потеря
    внутри живого соединения.

``lost`` на ``/check/sensor``
    Потери на best-effort ожидаемы и сами по себе дефектом не являются.

``gaps`` / ``duration``
    Смотреть надо не на факт перерыва, а на его длину относительно самого
    обрыва. Здесь сеть отсутствовала 15 секунд, а перерыв в данных
    составил 34.8 — около двадцати секунд ушло на переустановление
    TCP-соединения и повторное согласование endpoints уже после того, как
    сеть вернулась. Это и есть цена одного обрыва: столько времени на
    ноутбуке не будет ни телеметрии, ни картинки в RViz, хотя на роботе
    всё продолжает работать.

``/check/latched: after_s``
    Сколько секунд после подписки пришло удержанное значение. Малое число
    подтверждает late-joiner: RViz получит ``/tf_static`` и карту сразу
    при подключении, а не будет ждать следующей публикации.

``jitter_stdev_ms`` / ``interval_max_ms``
    Разброс канала внутри живого соединения, без обрыва. Абсолютная
    задержка не измеряется, потому что часы машин не синхронизированы.
    Для RViz ``interval_max_ms`` важнее среднего — именно он даёт рывки
    в отображении.

Эти цифры — не норматив, а форма отчёта: локальная сеть здесь виртуальная,
физического канала нет вовсе. На Raspberry Pi по Wi-Fi ``jitter_stdev_ms``
и время переустановления TCP будут другими, и сравнивать их надо
с измерением на самом роботе, а не с этим прогоном.

Частые ложные срабатывания
-----------------------------

Четыре причины ниже дают одну и ту же картину: контейнеры запущены,
TCP-соединение установлено, в логах Router нет ни ошибок, ни предупреждений,
а данные не идут. Отличить их можно только измерением.

.. list-table::
   :header-rows: 1
   :widths: 30 40 30

   * - Причина
     - Как узнать
     - Где лечится
   * - :ref:`transport-check-ipc`
     - Не проходит даже локальный ``ros2 topic echo`` между контейнерами
       с общим сетевым namespace.
     - ``ipc:`` рядом с каждым ``network_mode:``
   * - :ref:`transport-check-address-mismatch`
     - ``ss -tni`` на сервере: соединение ``ESTABLISHED``, но
       ``bytes_sent`` — единицы байт в секунду, а не килобайты.
     - ``listening-addresses`` в ``ddsrouter/*.yaml``
   * - :ref:`transport-check-router-qos`
     - В логе RViz — ``incompatible QoS``, ``DURABILITY_QOS_POLICY``.
       Для best-effort сообщения в логе нет вовсе.
     - секция ``topics`` в ``ddsrouter/*.yaml``
   * - :ref:`transport-check-echo-qos`
     - ``ros2 topic echo`` молчит с явным ``--qos-*``, но отвечает
       без него.
     - способ проверки, не схема

.. _transport-check-ipc:

``network_mode`` без ``ipc``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Fast DDS определяет «один хост» по сетевому окружению и для участников
на одном хосте выбирает shared memory. И ``network_mode: host``, и
``network_mode: "service:X"`` делают контейнеры одним хостом, но
``/dev/shm`` у каждого контейнера свой, и согласованного транспорта
физически не существует. Обмен прекращается ещё до Router — на локальном
плече до него.

**Лечение**: рядом с каждым ``network_mode`` ставится ``ipc``. Донор
объявляется ``ipc: shareable``, присоединяющийся — ``ipc: "service:X"``.
При ``network_mode: host`` парой идёт ``ipc: host``.

.. _transport-check-address-mismatch:

``listening-addresses`` не совпадает с адресом подключения
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``ip`` в ``listening-addresses`` — это адрес, который Router *объявляет*
удалённой стороне, а не адрес привязки: слушает он на всех интерфейсах
независимо от этого значения. Router с заведомо чужим адресом в конфиге
стартует без замечаний.

Fast DDS сопоставляет объявленный локатор с уже открытым TCP-соединением.
При несовпадении сопоставления не происходит: служебный обмен идёт,
топики на удалённой стороне видны, endpoints создаются, а данные не идут
ни по одному топику.

**Лечение**: указывать тот адрес, который набирает клиент. Для Raspberry
Pi это её адрес в локальной сети (``PI_ADDRESS``, см. :ref:`Подготовку
<transport-check-prep>`), для локальной репетиции —
``host.docker.internal``. Ни ``0.0.0.0``, ни собственный адрес контейнера
не годятся.

.. _transport-check-router-qos:

QoS собственных endpoints Router
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Router не пробрасывает сообщения насквозь: он создаёт собственные
endpoints и согласуется с настоящими участниками по обычным правилам DDS.
По умолчанию эти endpoints reliable и volatile, поэтому best-effort и
удерживаемые топики не согласуются и молча не проходят — ровно те, ради
которых схема и строится.

**Лечение**: секция ``topics`` в конфигах **обеих** сторон —
``durability: true`` для ``/tf_static``, ``/map`` и прочих удерживаемых,
``reliability: false`` для лидара. Секция задаёт только QoS и
маршрутизацию не ограничивает: не перечисленные в ней топики идут с QoS
по умолчанию.

.. _transport-check-echo-qos:

Принудительный QoS у ``ros2 topic echo``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Это ошибка не схемы, а способа проверки. ``ros2 topic echo`` без ключей
QoS согласуется с найденным публикатором автоматически. Указанный вручную
``--qos-durability transient_local`` отключает автоматическое согласование,
и на топике с несколькими публикаторами echo молчит, хотя данные идут.

**Лечение**: проверять без ключей QoS. Если без них echo молчит, а с ними
работает, проблема в схеме, а не в команде.

.. _transport-check-next:

Дальше
------

После того как транспорт признан рабочим, к нему подключаются пакеты
проекта. Порядок при этом такой: SLAM, EKF, драйверы и
``rtk2026_observability`` работают на Raspberry Pi, а на ноутбуке остаётся
только RViz как подписчик.

Диагностика не переносится на ноутбук намеренно. ``rtk2026_observability``
опирается на ROS graph: ``topic_monitor`` в режиме ``graph_only``
использует ``get_publishers_info_by_topic``, ``node_monitor`` —
``get_node_names_and_namespaces`` и ``get_service_names_and_types``. Через
DDS Router граф не проходит достоверно, поэтому такие проверки должны
выполняться там, где граф настоящий. Сами топики ``/diagnostics`` и
``/diagnostics_agg`` при этом маршрутизируются нормально, и смотреть их
с ноутбука можно.

.. warning::

   Serial-порт Arduino может держать только один процесс. ``arduino_bridge``
   из ``rtk2026_driver``, ``link_server.py`` из стенда настройки моторов
   и прошивка через avrdude обращаются к одному устройству ``/dev/arduino``
   и одновременно работать не будут. Подробнее в :doc:`bench`.
